# 2026-08-24 GCash 两账号端到端验收

## 验收范围

本次使用两个全新 Gmail Catch-all 别名和两个固定 PH 代理 SID。每个账号在注册和提链阶段使用同一节点，注册结束后不执行 Session/AT 健康探测。提链任务设置 `max_attempts=1`，只验证能否生成 GCash 链接，不扫码、不支付。

临时上下文、代理清单和执行脚本全部位于两个项目各自的 `.tmp/`，验收后已从本机与服务器删除。Git、技术文档和日志中未写入原始代理凭据、AT 或 Session Token。

## 提链结果

两个账号均满足以下条件：

- `proxy_test` 完成，出口定位为马尼拉链路；
- `session_cookie=true`；
- `registration_device=true`；
- `browser_profile=chrome136`；
- `proxy_affinity=true`，匿名引用与注册结果一致；
- 外层 `attempts_used=1`，没有跨节点或跨设备重试。

两个账号均在 `create_checkout` 失败。第一次建单收到异常活动响应后，链路在同一会话生成 `chatgpt_checkout` Sentinel 并重试；第二次仍返回：

```text
Our systems have detected unusual activity. Please try again later.
```

两次诊断共同显示：

```text
frontend_context observation=False session=True build=True
```

任务没有进入 `configure_taxes`、`confirm_payment`、`start_payment` 或 `follow_redirect`，因此本次失败与 GCash cpmt 解析、Adyen 跳转、二维码监控或支付回调无关。

## 已证实结论

1. 之前“只传 AT 导致设备、Session 和节点全部变化”的项目问题已修复；真实任务确认四项上下文均被复用。
2. 四段式代理与标准 URL 的匿名引用已经统一，本次无备用节点警告。
3. 注册账号不是在注册阶段直接失败；两个账号都产出 Free Session 和试用资格。
4. 当前真实阻塞点是 ChatGPT Checkout 建单接口的异常活动判定。
5. 收敛后的重试策略生效：Sentinel 同会话重试仍失败后立即终止，没有连续消耗多个代理节点。

## 仍待验证因素

- `x-oai-is-client-observation` 未被临时 Playwright 前端上下文捕获；它与异常活动拒绝同时出现，但本次数据不足以证明单一因果关系。
- GCash 项目随仓库固定的 Sentinel 版本为 `20260219f9f6`，且执行本地冻结 SDK 资源。当前时间为 2026-08-24，该资源是否仍被上游完整接受需要独立验证。
- 两个账号均为注册后立即建单的新账号，账号年龄、代理供应商网段信誉、同批注册特征或优惠活动本身都可能参与上游判定。

为控制代理成本和账号风险，本次没有继续增加账号、换节点或重复建单。

## 后续工程方向

若继续推进，应把实验变量限定为一个：优先让 Checkout 的 Sentinel 与前端观察上下文来自同一个实时浏览器会话，并记录当前 Sentinel SDK 版本、观察头是否存在和首个建单请求是否已携带 Sentinel。完成离线测试后，再使用一个账号、一次请求做对照验收。

另一条路线是把 Checkout 创建也迁入真实浏览器上下文，而不只用 Playwright 采集部分头/Cookie 后切回 `curl_cffi`。该路线改动和流量成本更高，需要单独立项。
